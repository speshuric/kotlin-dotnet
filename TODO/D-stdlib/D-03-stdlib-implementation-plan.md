  (решения Р1–Р4, ADR 0014), F-03 слой 0.2 (обобщение CustomAttribute — параллельный трек)
- **Статус:** WIP (план утверждён в интервью 2026-08-27)

## Отношение к D-01/D-02

- **D-01** (каркас stdlib): поглощается шагом 4. Отличие от текста D-01:

## Шаги

### Шаг 1. Чтение аннотаций из IR (+ инструментальная видимость) — DONE (2026-08-28)

Реализация: StdlibAnnotations.kt (реестр + ридер AnnotationReader),
секция recognized-annotations в ir-dump, ключ dump-grep в тест-формате,
e2e-тест 06-annotations. Нюанс версии: IrAnnotation — это
IrConstructorCall без typeRef; класс аннотации резолвится через
symbol.owner (IrConstructor).parent;

- В `DotnetIrVisitor` научиться извлекать аннотации деклараций через
  `IrAnnotationContainer.annotations` (механика — §5 дизайн-дока).
- Расширить ir-dump: печатать fqName распознанных аннотаций на узлах,
  чтобы отладка чтения не требовала отладчика.
- Эксперимент: файловые таргеты (`@file:...`) — проверить видимость
  через IrFile/IrModuleFragment, результат зафиксировать в дизайн-доке.

Приёмка: тестовый проект с локально объявленной аннотацией; дамп
показывает её распознавание на классе/функции.

### Шаг 2. Реестр переносов вместо разрозненных when (этап A) — DONE (2026-08-28)

Реализация: StdlibMapping.kt — запись Entry(fqName, owner, method) на
символ; callSignature строит операнд CALL из фактических типов
аргументов (перегрузки резолвятся в точке вызова, как в Print.cs).
StdlibResolver стал тонким фасадом (isStdlibCall + resolveStdlibCall на
одной таблице — расхождение «знаем/не знаем» невозможно). Поля записи
совпадают по смыслу с будущей аннотацией перенаправления
(Р2 дизайн-дока): fqName, owner, method.

Историческое описание шага:

- Вынести таблицу из `StdlibResolver` в `StdlibMapping.kt`: одна
  структурированная запись на символ (fqn, сигнатура параметров, target).
- Поля записи совпадают по смыслу с будущей аннотацией перенаправления
  (см. Р2 дизайн-дока) — чтобы конвертация была механической.
- Поведение компиляции не меняется; `needsRuntime` консолидируется с той же
  таблицей.

Приёмка: `just test-all` зелёный без изменений ожиданий.

### Шаг 3. Режимы строгости (`stdlib.mode`) — DONE (2026-08-28)

Реализация: StdlibMode.kt (enum + UncoveredStdlibCollector), CLI-опция
stdlib.mode (валидация на parse), фасад extension'а применяет политику
после эмиссии; точка учёта — предусловие emitUserTopLevelCall
(kotlin.* callee без тела в файле) + ветка нулевого резолва
StdlibResolver. Отказной e2e-тест: kind=negative в build-test.sh
(компиляция обязана упасть, expect — подстрока текста ошибки).
Дефолт пока lenient (в strict все текущие тесты зелёные — переключение
дефолта отдельным решением).

Историческое описание шага:

- Новая CLI-опция плагина: `stdlib.mode=lenient|strict`.
- Сбор фактов о неперехваченных `kotlin.*` вызовах за проход модуля;
  выдача одним сводным списком.
- `strict`: компиляция завершается ошибкой со списком (диагностику K2 из
  IR-extension отдать нельзя — PoC-механика: исключение после генерации;
  при реализации поискать канал сообщений фронта).
- `lenient`: сегодняшнее поведение + предупреждение о каждом символе.
- Дефолт на первом шаге — lenient; переключение дефолта на strict —
  после зелёного прогона всех тестов в strict.

Приёмка: см. §6 дизайн-дока (п. 2).

### Шаг 4. Каркас :libraries:stdlib (этап A, вне pipeline)

- Gradle-модуль `kotlin-dotnet-engine/libraries/stdlib` (раскладка Р4):
  пакеты `kotlin/io`, `kotlin/text`, `kotlin/collections`,
  `kotlin/dotnet/annotations`.
- Аннотации: `@DotnetName(name)`, `@KotlinToPascalCase`,
  `@DotnetFromPascalCase` — SOURCE retention, targets по F-03 слою 0.
  Механика обработки — существующими шагами / F-треком.
- Шимы — декларации с телами-заглушками; к пользовательской компиляции
  НЕ подключены.
- Минимальный состав деклараций сверять с апстримом
  (`.sources/kotlin/libraries/stdlib/common/src` + `js/src`) и каталогами
  `*-minimal-for-test`.

Приёмка: модуль собирается обычным kotlinc (.sdk/jdk toolchain);
в пользовательской компиляции не участвует.

### Шаг 5. Переключатель --own-stdlib (этап B, один тест)

- Скрипт: сборка нашего stdlib-jar обычным kotlinc; компиляция одного
  e2e-теста с `-Xno-stdlib -cp <наш>.jar`; путь println/print работает.
- Если фронту не хватает деклараций Intrinsics (диапазоны, `listOf`,
  enum entries...) — докупировать недостающее из upstream common/js;
  целевой ориентир — самодостаточный минимальный набор.
- Реестр (шаг 2) продолжает обслуживать перенаправления в режиме B.

Приёмка: см. §6 дизайн-дока (пп. 4–5).

### Шаг 6. Финал Р2: резолвер по IR-аннотациям шимов

- Шимы аннотируются; resolver предпочитает IR-аннотации реестру;
  реестр остаётся для символов без мигрированных шимов (режим A).

Приёмка: один и тот же тест даёт одинаковый вывод в режимах A и B.
