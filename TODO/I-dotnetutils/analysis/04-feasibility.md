# Analysis 04: Feasibility assessment

- **Задача:** [I-01](../I-01-metadata-builder.md)
- **Статус:** на утверждении
- **Вход:** analysis/01–03, ADR 0009

## Вердикт

**Подход реализуем.** Перенос — механическая трансляция с ограниченным
набором нетривиальных мест, все они локализованы и покрыты стратегией
верификации. Основания:

1. **Нет жёстких зависимостей** (analysis/02): всё заменяется
   kotlin-stdlib или ручной записью байтов; криптографии, Win32,
   unsafe-инфраструктуры в write-path нет.
2. **Объём известен и конечен**: ~14 250 строк C#, ~50 типов
   (analysis/01, 03); делится на независимые блоки ≤10 тыс. строк.
3. **Эталонные тесты есть**: юнит-тесты SRM переносятся частично
   (внутренние проверки), round-trip закрывается C#-harness'ом на
   настоящем SRM + e2e `just test`.
4. **Таблица опкодов уже машиночитаема** (ILOpCode enum), транскрипция
   из PDF не требуется.
5. **Проверено на практике**: аналогичный по природе перенос
   (тексто-ориентированный IL → структурированные вызовы) уже выполнен
   в проекте (IlEmitter); здесь меняется только целевой формат.

## Нетривиальные места (реестр)

| # | Место | Риск | Митигация |
|---|---|---|---|
| N1 | `BlobUtilities`: LE-запись примитивов, guid reorder (mixed-endian), UTF-8 кодировщик | побайтовые расхождения | golden-тесты против C#-harness; тесты BlobUtilitiesTests оригинала |
| N2 | Compressed integers (`BlobWriterImpl`) | граничные значения (0x7F/0x3FFF/…) | родные тесты + property-тест на диапазонах |
| N3 | Раскладка PE (`ManagedTextSection`, IAT, alignment) | EXE не запускается | e2e: запуск реального EXE через dotnet |
| N4 | Таблица метаданных: coded indexes, row layout, heaps (#Strings suffix-sort) | невалидная сборка | C#-harness открывает наш DLL настоящим MetadataReader'ом |
| N5 | `kotlin.uuid.Uuid` (experimental API) | изменение/удаление API в будущих Kotlin | opt-in изолирован модулем; escape-hatch — собственный класс (analysis/02 §E) |
| N6 | Отсутствие seekable stream (память→файл) | рост памяти на больших сборках | для PoC некритично (килобайты); помечено временным |

## Ограничения подхода (осознанные)

- Дифф против апстрима SRM ведётся вручную; write-path апстрима
  стабилен годами — риск низкий.
- До завершения переноса поддерживаются оба пути генерации (ilasm
  остаётся до переключения compiler-plugin).
- Производительность JVM-версии не цель PoC (замер после первого EXE).

## Критерий успеха этапа

EXE/DLL, собранный целиком Kotlin-кодом модуля dotnetutils:
1) открывается настоящим SRM без ошибок (C#-harness);
2) проходит существующие e2e-тесты проекта (`just test`);
3) обратное дизассемблирование (`dotnet-ildasm`) даёт корректный,
   ожидаемый IL и метаданные. Побайтовое совпадение всей сборки с
   эталоном **не требуется** (MVID/stamp рандомизированы даже у двух
   запусков одного компилятора). Локальные golden-сверки допустимы
   только на юнит-уровне для фиксированных байтовых областей
   (guid layout, заголовки, compressed integer'ы).
