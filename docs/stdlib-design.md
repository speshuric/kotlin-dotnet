# Дизайн stdlib для Kotlin → .NET

> **Статус:** черновик, согласованный в интервью (2026-08-27).
> Развилки зафиксированы в разделе «Решения»; реализация — по плану ниже.
> Связанные документы: [`TODO/D-stdlib/`](../TODO/D-stdlib/), ADR 0002 (runtime),
> [`docs/identifier-mapping.md`](identifier-mapping.md) (F-03), ADR 0005.

## 1. Проблема

Сегодня источником деклараций stdlib для пользовательского кода служит
родной kotlin-stdlib, который kotlinc кладёт на classpath. Плагин
перехватывает известные вызовы (`StdlibResolver`: `kotlin.io.println/print`
→ `Kotlin.Runtime.Print`); остальное из `kotlin.*` проходит мимо resolver'а
и либо попадает в неразрешимые JVM-тела, либо молча теряется. Поверхность
API не контролируется: непонятно, что «есть», а что «ещё не сделано».

Параллельно для F-трека (мэппинг имён) нужны собственные аннотации
(`@DotnetName` и ко.), которым нужно место в компилируемом коде.

## 2. Образец: upstream kotlin-stdlib (common + js)

Источник образца — `.sources/kotlin/libraries/stdlib/`:

- **Многослойность:** `common/` (expect-декларации) + `js/` (actual + шимы).
  Для одного таргета .NET expect/actual вырождается — реализации пишем сразу.
- **Шимы на Kotlin:** даже `println` — шим поверх платформенного примитива
  (`js/src/kotlin/console.kt`: `BaseOutput` → `NodeJsOutput`/`BufferedOutputToConsoleLog`,
  `public actual fun println(...) = output.println(...)`). У нас ту же роль
  играет C# `Kotlin.Runtime.Print`.
- **Неявные импорты** — конфиг фронта (`DefaultImportsProvider`, платформенные
  наследники `JvmDefaultImportsProvider`, wasm-провайдеры). Список пакетов
  зашит в анализаторе и НЕ зависит от того, какой модуль даёт эти пакеты:
  свои декларации в `kotlin.io` автоподстановку импортов сохраняют.
- **Прецедент переименований:** `@JsName` — работающий механизм внешних имён,
  модель для наших трансляционных аннотаций.
- **Каталоги минимальных stdlib для тестов** (`js-ir-minimal-for-test`,
  `jvm-minimal-for-test`, `jklib-for-test`) — чек-лист того минимума
  деклараций, без которого фронтенд отказывается жить.

## 3. Решения (зафиксированы в интервью)

### Р1. Модель stdlib — гибрид A→B

1. **Сейчас (этап A):** родной classpath остаётся источником сигнатур;
   таблица переносов выносится из кода; добавляется учёт покрытия вызовов
   `kotlin.*` и режим строгости (см. Р3). Каркас собственного stdlib
   строится параллельно, к пользовательской компиляции не подключён.
2. **Потом (этап B):** собранный наш stdlib-jar подставляется вместо
   родного через `kotlinc -Xno-stdlib -cp <наш>.jar`. Переключатель —
   опция скрипта `kotlinc-net.sh --own-stdlib` (фича-флаг уровня сборки,
   НЕ языка), включается сначала на одном тесте, затем становится дефолтом
   после стабилизации набора деклараций.

Сосуществование родной и нашей stdlib с одинаковыми пакетами `kotlin.*`
на одном classpath невозможно (redeclaration) — поэтому только «либо A,
либо B», никаких смешанных состояний.

### Р2. Таблица переносов — аннотации на шимах

Целевая форма: перенаправление `fqn → runtime` описывается **аннотациями
на декларациях-шимах в нашем stdlib**, плагин читает их из IR (см. §5).

Переходные состояния:
- **Переходный период (этап A):** пока каркас stdlib не встал на
  компиляцию, действует декларативный реестр в коде плагина
  (`StdlibMapping.kt`: структурированная запись на символ, не разбросанные
  when-ветки). Реестр проектируем совместимым по смыслу с будущими
  аннотациями: те же поля (fqname, целевая сигнатура).
- **Финал (этап B):** шимы аннотированы, resolver ходит по IR деклараций;
  реестр удаляется или остаётся для символов, чьи шимы ещё не мигрированы.

### Р3. Политика неперехваченных вызовов

Новая CLI-опция плагина `stdlib.mode`:
- `strict` (дефолт после внедрения): любой `kotlin.*` вызов без покрытия
  = ошибка компиляции со **сводным списком** всех необслуженных символов
  модуля (собирается за проход, выдаётся одним списком);
- `lenient`: сегодняшнее поведение + предупреждение о каждом необслуженном
  символе; предназначен для экспериментов и разведки новых API.

Тихих заглушек (`NotImplementedException` в местах вызова) не генерируем.

### Р4. Раскладка каркаса — один модуль, зеркальные пакеты

```
kotlin-dotnet-engine/
└── libraries/
    └── stdlib/                     # Gradle-модуль :libraries:stdlib
        ├── build.gradle.kts        # чистый Kotlin JVM-модуль (как dotnetutils)
        ├── README.md
        └── src/main/kotlin/
            ├── kotlin/io/          # println/print/readLine (шимы)
            ├── kotlin/text/        # length/substring/... (по мере покрытия)
            ├── kotlin/collections/ # listOf/mapOf/setOf/...
            └── kotlin/dotnet/
                └── annotations/    # @DotnetName, @KotlinToPascalCase, ...
```

Без expect/actual (таргет один). Пакетная структура копирует upstream —
это гарантирует работу неявных импортов и упрощает дифф с апстримом при
копировании деклараций.

## 4. Runtime (C#-часть)

Сейчас — только `Print.cs`. Конвенция закладывается заранее: **имена точек
входа runtime станут целевыми именами для аннотаций перенаправления**
(`@DotnetName("Kotlin.Runtime.Print.println")`). Runtime расширяется по мере
покрытия stdlib (readLine → `Stdio`, строки → `Strings`, коллекции →
`Collections`) — см. AGENTS.md §Runtime.

## 5. Чтение аннотаций из IR (технический дизайн)

Почти все IR-узлы наследуют `IrAnnotationContainer` с полем
`val annotations: List<IrAnnotation>`
(`.sources/kotlin/compiler/ir/ir.tree/src/org/jetbrains/kotlin/ir/declarations/IrAnnotationContainer.kt`).

Проверено по исходникам апстрима (v2.4.20-RC) и экспериментом с плагином:
- контейнер аннотаций — `IrAnnotationContainer` (`val annotations:
  List<IrAnnotation>`); **`IrFile` его реализует**
  (`compiler/ir/ir.tree/gen/.../IrFile.kt: IrFile : IrPackageFragment(),
  IrMutableAnnotationContainer, ...`), т.е. файловые таргеты (`@file:`)
  доступны тем же доступом, отдельного канала не требуется;
- **`IrConst` в этой версии НЕ дженерик** (`gen/.../IrConst.kt`):
  `abstract var value: Any?`, тег — `kind: IrConstKind` (sealed class,
  `IrConstKind.String` и т.д.); строковый аргумент аннотации —
  приведение к `IrConst` + проверка kind;
- значение берётся из `annotation.arguments[i]` (обычные Ir-выражения).

Алгоритм чтения своего трансляционного атрибута:
1. В visitor'е на узле-цели (класс/функция/property/поле/конструктор)
   пройтись по `declaration.annotations`;
2. Из `annotation.typeRef.classOrNull?.owner` взять fqName класса-аннотации
   и сопоставить с реестром распознаваемых имён
   ([StdlibAnnotations] в компиляторе; до появления нашего пакета допускается
   совпадение по простому имени — см. комментарий в файле);
3. Значение — из `annotation.arguments[i]`: `(arg as? IrConst)` с kind String.

Свойства аннотаций:
- Наши аннотации **не эмитируются** в метаданные результирующей сборки
  на этом шаге (их смысл — инструкция компилятору).
- Эмиссия произвольных аннотаций в CustomAttribute — отдельная задача
  (обобщение `addCustomAttribute`, план F-03 слой 0.2).

## 6. Критерии проверки

1. `just test-all` зелёный в обоих режимах (debug/release) — регрессия
   не сломана (этап A не должен менять поведение существующих тестов,
   кроме появления предупреждений в lenient-режиме).
2. Тест на strict-режим: входной файл с заведомо неперехваченным
   `kotlin.*` вызовом → ошибка компиляции, текст содержит fqn символа.
3. Тест чтения аннотаций: IR-dump показывает распознанный
   `@DotnetName` на шиме (unit/e2e — уточняется в плане).
4. Этап B: e2e-тест собирается с `--own-stdlib`; результат PE сопоставим
   по семантике с этапом A (тот же вывод запуска).
5. Формат таблицы реестра допускает механическую конвертацию в аннотации
   (одна запись = один символ, поля совпадают с параметрами аннотации).
