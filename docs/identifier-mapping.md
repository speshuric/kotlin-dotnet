# Kotlin ↔ .NET: спецификация маппинга идентификаторов

Черновик спецификации. Стабильные части отмечены **[решено]**;
остальное — проектные договорённости, подлежащие верификации по мере
имплементации.

Легенда для колонок «Kotlin → .NET» / «.NET → Kotlin»:

- **не менять** — имя переносится буквально
- **не экспортируется** — идентификатор отсутствует в публичных
  метаданных сборки (или не участвует в маппинге)
- **camelCase↔PascalCase** — меняется регистр первой буквы (и только
  первой — само разбиение на слова не трогается)
- **+/- префикс/суффикс** — при экспорте добавляется, при импорте
  убирается (симметрично)
- **атрибут** — используется механизм `KotlinIdentifier` (см. ниже)
- **особый механизм** — см. примечание, стандартные варианты выше не
  подходят

## Механизм сохранения происхождения: атрибут `KotlinIdentifier`

Каждый экспортируемый из Kotlin в .NET символ дополнительно снабжается
синтетическим атрибутом (условное имя `KotlinIdentifierAttribute`),
хранящим исходное kotlin-имя. Решение «использовать имя из атрибута или
применить эвристику» принимается локально по каждому символу
(наличие/отсутствие атрибута) — отдельный флаг уровня сборки не
требуется.

**Версионирование схемы (решено):** атрибут обязательно несёт номер
версии схемы. **v0.01** — минимальная версия, только имя, без
дискриминатора вида элемента. Дискриминатор (`Kind`: companion-член,
enum entry и т.п.) — задел на будущую версию схемы, чтобы расширение не
ломало более старых потребителей.

Ориентировочная форма (v0.01):

```
KotlinIdentifierAttribute(string originalName, int schemaVersion = 1)
```

## Прецеденты из Kotlin/JVM и Kotlin/JS

Исследование того, когда и почему сам Kotlin манглирует имена при
компиляции в JVM/JS, и что из этого переносится на .NET.

| Механизм у Kotlin | Причина в целевой платформе | Переносится на .NET? |
|---|---|---|
| `internal` → манглируется в public+суффикс модуля на JVM | У JVM нет реальной видимости «на модуль»; манглирование — единственный способ сымитировать её и не допустить случайных переопределений/использований из Java | **Нет.** У CLR `internal` — по-настоящему enforced видимость на уровне сборки (проверяется загрузчиком/JIT). Манглировать нечего — прямое отображение `internal` → `internal` достаточно |
| `value`/`inline`-классы → хэш-суффикс к функциям на JVM (`validate-3mN7H-Y`) | JVM стирает inline-класс до базового типа, отсюда угроза коллизии сигнатур; суффикс с намеренно недопустимым для Java символом `-` | **Нет,** если маппить `value class` в настоящий CLR `struct` — первоклассный, не стираемый тип. Стирание было костылём, вынужденным отсутствием value-типов на JVM |
| Почти всё манглируется по умолчанию на JS (`@JsExport`/`@JsName` — способ получить стабильное имя) | В JS нет перегрузки функций — без манглирования вторая перегрузка сломала бы первую | **Нет** — у .NET, как и у JVM, есть настоящая перегрузка по типам параметров |
| Поля/свойства всегда через синтетический getter на JS | В JS нет «чистого экспортируемого поля» на уровне модели компилятора | **Нет** — у CLR, как и у Kotlin, свойство — полноценная метаданная-сущность (уже учтено) |
| `@kotlin.Metadata` — плотная версионированная аннотация на каждом class-файле, хранящая исходную Kotlin-структуру для компилятора/рефлексии | Байткод/JS в принципе теряют часть Kotlin-модели | Прямой аналог того, что вы уже делаете (`KotlinIdentifier` + обязательная версия), только у Kotlin это один плотный блоб на класс, а не атрибут на член. Полезный образец для будущей версии схемы, если per-member атрибуты станут громоздкими — не актуально для v0.01 |
| Case-insensitive ФС + «один класс = один файл» → случайная порча сборки на Mac/Windows при коллизии имён только по регистру (в т.ч. синтетических: лямбды, названные по внешней локальной переменной, бэктик-тесты). Всё ещё открыто в трекере (KT-81559, сентябрь 2025) — компилятор не предупреждает | Корень — конвенция «класс = файл на диске» + ОС, а не сам JVM-формат | **Нет для итоговой сборки** — CLR хранит типы как строки в таблицах метаданных внутри одного PE-файла, ФС в разрешении имён не участвует, баг структурно невозможен. **Но да — для собственного тулинга компилятора**, если когда-нибудь появится покомпонентный build-кэш/генерация с конвенцией «файл = сырое имя типа». Не ключевать такие файлы сырым именем — хэш или case-safe кодирование |

**Дополнительно, из ECMA-335/CLS:** правило CLS прямо гласит, что два
идентификатора, различающиеся только регистром, для целей
CLS-совместимости считаются одинаковыми — это в точности риск
«коллизия при совпадении по регистру первой буквы» для методов/свойств.
В отличие от JVM-версии этой же проблемы (ОС-зависимая, «работает на
Linux CI, падает на маке коллеги»), наша — полностью детерминирована:
коллизия после camelCase→PascalCase либо есть, либо её нет, одинаково
на любой машине. **Решение:** компилятор безусловно детектирует такие
коллизии на этапе компиляции (независимо от решения про
`[CLSCompliant]`, которое отдельно решает другой вопрос — заявлять ли
эту гарантию внешним потребителям).

## Таблица

| Вид идентификаторов | Kotlin | C# (.NET) | Kotlin → .NET | .NET → Kotlin | Примечания |
|---|---|---|---|---|---|
| Классы, enum class, annotation-классы (не object, не companion) | `PascalCase` | `PascalCase` | не менять | не менять | Имя и так lossless, атрибут не обязателен |
| `object` (top-level/nested, не companion) | `Foo` — одно имя служит и типом, и значением-синглтоном | `Foo`-тип + `Instance`-accessor | не менять (тип, + атрибут); `Instance` синтезируется всегда | тип — как обычный class; `Instance` — по структурному признаку | Детали и обоснование имени `Instance` — в разделе «Политика для object/companion» ниже |
| `value class` / `inline class` (`@JvmInline`), `data class` (только `val`, без циклов) | `PascalCase`; на JVM/JS value/inline стирается до базового типа (источник манглирования там) | `value class`/`inline class` → `readonly struct`; `data class` → `readonly record struct` (авто-генерируемые `Equals`/`GetHashCode`/`ToString`/`Deconstruct` и `with`-выражение почти 1:1 ложатся на `equals`/`hashCode`/`toString`/`componentN`/`copy()`) | **[решено]** маппить в struct-семейство | struct-семейство → `value class`/`data class` соответственно | **Обнаруженный факт (зафиксировано):** самоссылающееся поле struct своего же типа невозможно на уровне CLR (в т.ч. через `Nullable<T>`) — **решение:** такое поле транслируется через индирекцию (ссылочную обёртку), а не весь тип целиком уходит в `class`. **`data class` с `var`:** сознательно НЕ маппится в struct (меняется семантика мутации через алиасы) — уходит в `sealed record` (обычный reference-type record, чтобы сохранить авто-`Equals`/`with`/`Deconstruct`) |
| Интерфейсы | `PascalCase`, без префикса | `PascalCase` + префикс `I` | + префикс `I`, + атрибут | атрибут → исходное имя буквально; без атрибута → эвристика: снять `I` | Эвристика остаётся нужна только для чужих .NET-интерфейсов |
| `companion object` | та же природа, что `object` (см. выше); по умолчанию безымянный, имя внутри — `Companion` | тот же class+`Instance`, что у object, **плюс** static-redirect методы на охватывающем классе | тип — как у object; redirect-статики генерируются автоматически, для удобства вызова из C# | redirect-статики избыточны, при обратном импорте игнорируются — источник истины сам companion-object (импортируется по object-политике) | Не отдельный случай, а частный случай object — см. «Политика для object/companion» ниже |
| Методы (public / protected) | `camelCase` | `PascalCase` | camelCase→PascalCase, + атрибут | атрибут → исходное имя; без атрибута → эвристика PascalCase→camelCase | `protected` трактуется как public |
| Свойства (public / protected) | `camelCase` | `PascalCase` | camelCase→PascalCase, + атрибут | то же, что для методов | — |
| Параметры функций/методов | `camelCase` | `camelCase` | не менять | не менять | Совпадает по конвенции в обоих языках |
| Локальные переменные | `camelCase` | `camelCase` | не экспортируется | не экспортируется | Живут только в debug-информации |
| Константы (`const val` / `const`) | `UPPER_SNAKE_CASE` | `PascalCase` | **[решено]** один экспортируемый член в `PascalCase` + атрибут с исходным `UPPER_SNAKE_CASE`; дублирования нет | атрибут → исходное имя буквально | — |
| private-члены (методы, свойства, поля, включая backing-поля) | `camelCase` | методы/свойства — `PascalCase` по общему стилю, поля — `_camelCase` (де-факто конвенция) | не менять (как есть, без преобразования регистра) | не менять (как есть) | Физически присутствуют в метаданных с `private`-видимостью — это не «не экспортируется», а «видны только через reflection и не гарантированы»; доступность через reflection — забота потребителя, не компилятора |
| internal-члены (методы, свойства) | `camelCase` | `internal`, `PascalCase` по общему стилю | camelCase→PascalCase, + атрибут — как у public/protected, без доп. манглирования | атрибут → исходное имя; без атрибута → эвристика как у public | **[решено]** манглирование (как на JVM) не нужно — CLR `internal` реально enforced на уровне сборки, в отличие от JVM. Условие: границы «модуль» (Kotlin) и «сборка» (.NET) должны совпадать в модели компилятора |
| Атрибуты / аннотации (attribute-классы) | `PascalCase`, без суффикса | `PascalCase` + суффикс `Attribute` (опускается при применении) | + суффикс `Attribute`, + атрибут | атрибут → исходное имя; без атрибута → эвристика: снять `Attribute` | — |
| Пакеты / namespace | `lowercase`, точечная нотация | `PascalCase` на каждый сегмент | капитализировать сегменты + assembly-level атрибут-таблица `namespace → kotlin package` | атрибут-таблица → исходный путь буквально; без атрибута → эвристика lowercase (lossy для составных сегментов) | **[решено]** список пар на уровне сборки, не на уровне отдельных типов |
| Параметры типов (generics) | `T`/`K`/`V` или описательный `PascalCase` | `T`+`PascalCase` | не менять | не менять | Идентично в обе стороны |
| Асинхронные функции | `suspend fun` | суффикс `Async` | не менять | не менять | Сигнатурный маппинг — отдельный вопрос |
| Идентификаторы с недопустимыми в C# символами (backtick-имена, тесты) | произвольная строка в бэктиках | ограничение синтаксиса C#-парсера и CLS-профиля (ECMA-335 CLS Rule 4); сырой формат метаданных (Partition II) сам по себе такой проверки не делает | **[решено]** без mangling по умолчанию — исходное имя переносится в IL как есть | не менять | Прецедент у самого Kotlin/JVM: суффикс `-` в имени inline-class-функций специально невалиден для Java — тот же принцип «пусть будет нечитаемо для целевого языка, зато точно». Для callable-из-C# имени — ручной override `@DotnetName` |
| Enum-значения (entries) | `UPPER_SNAKE_CASE` или `PascalCase` (оба разрешены) | только `PascalCase` | всегда `PascalCase` + атрибут с исходным именем в исходном регистре | атрибут → исходное имя буквально; без атрибута → оставить `PascalCase` как есть | — |

## Политика для object/companion

И `object`, и `companion object` компилируются в реальный класс +
статический singleton-accessor с фиксированным именем **`Instance`**.
Имя не выводится из kotlin-стороны и не подлежит
camelCase/PascalCase-конвертации — это чисто синтетический член. Выбор
имени не произвольный: повторяет собственную конвенцию Kotlin/JVM
(`object` на JVM компилируется в класс со статическим полем `INSTANCE`)
и общую .NET-конвенцию для синглтонов. **Коллизия:** если в
object/companion уже есть member, чьё PascalCase-имя ровно `Instance` —
нужен tie-break (переименование синтетического accessor либо
`@DotnetName` от пользователя).

**Companion — не исключение, а частный случай.** Companion хранит свой
объект как настоящий объект (может и сам держать `Instance` внутри),
просто не публикует его как основной способ доступа. По умолчанию (без
явного имени в Kotlin) тип называется `Companion` — как и в самом Kotlin.
Дополнительно на охватывающем классе генерируются static-redirect
методы — исключительно для удобства вызова из C# (`Foo.Method()` вместо
`Foo.Companion.Method()`), прямой аналог `@JvmStatic` у самого
Kotlin/JVM, только всегда включённый, а не opt-in.

Поскольку redirect-статики — чистая, не несущая уникальной информации
обёртка, при обратном импорте их можно просто игнорировать: источником
истины остаётся сам companion-object, импортируемый по той же
object-политике.

## Механизм ручных исключений (override)

Отдельный от `KotlinIdentifier` механизм — для намеренного управления
именами, а не для автоматического round-trip:

- **Уровень идентификатора** — аннотация `@DotnetName` (зафиксировано;
  аналог `@JvmName`/`@JsName`), переопределяющая правило из таблицы для
  конкретного элемента. В частности, пригодится для
  backtick-идентификаторов, если нужно дать им ещё и callable-из-C# имя.
- **Уровень скоупа** (модуль / вся сборка) — переключатели, отключающие
  автоматическую конвертацию имён в одном или обоих направлениях.
  Черновые имена `DisableKotlinToDotnetNameConversions` /
  `DisableDotnetToKotlinNameConversions` — по-прежнему нужны более
  удачные названия.

Важно: override меняет только .NET-facing имя.
`KotlinIdentifier`-атрибут должен хранить настоящее kotlin-имя, а не
override-имя — иначе round-trip даёт не исходное имя, а override-имя.

## Открытые вопросы

1. **Companion + v0.01** — нужен всего один бит-дискриминатор: «этот
   nested object — именно companion охватывающего класса», чтобы
   отличить от произвольного named nested object (redirect-статики
   отдельного признака не требуют — они игнорируются при импорте). Для
   v0.01 можно закрыть эвристикой по умолчанному имени `Companion` (для
   безымянных companion); явно названные companion (`companion object
   Utils`) в v0.01 при обратном импорте потеряют fidelity — вернутся как
   обычный nested object, а не `companion object`. Принимается как
   известное ограничение версии 0.01, либо на проработку, если это
   неприемлемо.
2. ~~`internal`~~ — **закрыто по манглированию:** прямое отображение
   `internal`→`internal` без спецобработки, CLR даёт реальную
   enforced-видимость. Остаётся только подтвердить, что «модуль» Kotlin
   и «сборка» .NET в модели компилятора — одно и то же.
3. ~~`value class`/`inline class`/`data class`~~ — **решено полностью:**
   struct-семейство для immutable-без-циклов случая; рекурсия —
   индирекция поля; `var` — `sealed record` вместо struct.
4. **CLS-совместимость сборки** — заявлять ли `[CLSCompliant(true)]`
   вообще (вопрос о гарантии для внешних потребителей типа VB.NET; сама
   детекция коллизий после camelCase→PascalCase теперь решена безусловно
   — см. раздел «Прецеденты» — и от этого флага не зависит).
5. Названия для scope-level переключателей
   (`Disable...NameConversions`) — черновые, требуют лучшего варианта.
