# Формат тестов (`test-projects/`)

Модель: **1 тест = 1 папка** внутри `test-projects/`. Имя папки = id теста
(`just test <id>`, селекторы `all`/`last`/`<glob>` работают по этим id).
Реестр имён нигде не хардкодится: список тестов получается обходом каталога.

## Структура папки теста

```
test-projects/<test-id>/
├── test.properties      # атрибуты теста (обязателен; без него папка — не тест)
├── <sources>.kt         # исходники (набор задаётся ключом sources)
├── csharp-test/         # опционально: C#-consumer для dll-тестов
└── README.md            # опционально: заметки по тесту
```

Артефакты сборки в репозиторий не попадают — они пишутся в `build/<test-id>/`.

## `test.properties`

Формат — упрощённые Java-properties, читаемые человеком и парсимые
`scripts/tests.sh` без внешних зависимостей:

- `key=value`, одна пара на строку; пробелы вокруг `=` и значения обрезаются.
- `#` в начале строки — комментарий.
- Значение — одна строка; `\n` внутри значения раскрывается при проверке
  вывода (`printf '%b'`), что позволяет задать многострочное ожидание.
- Пустое значение эквивалентно отсутствующему ключу.

| Ключ        | Обязателен | По умолчанию | Описание |
|-------------|------------|--------------|----------|
| `kind`      | да*        | —            | `exe` или `dll` |
| `backends`  | нет        | `pe`         | Единственное допустимое значение — `pe`. Значение `il` — ошибка конфигурации (IL-текст/ilasm-путь удалён, ADR 0012) |
| `sources`   | нет        | `*.kt`       | Glob исходников относительно папки теста. Несколько файлов = несколько программ: каждая собирается и проверяется отдельно |
| `consumer`  | для dll    | —            | Путь к C#-проекту-потребителю относительно папки теста |
| `expect`    | нет*       | —            | Ожидаемый stdout (`\n`-escape). Для `exe` — прогон собранного образа; для `dll` — stdout consumer'а. Без `expect` проверяется только непустота вывода |
| `desc`      | да*        | —            | Однострочное описание (показывается в списках тестов) |
| `type`      | нет        | `kotlin`     | `kotlin` — обычный тест; `gradle-image` — образ строит Gradle-тест модуля `dotnetutils` (исходников `.kt` нет) |
| `dump-grep` | нет        | —            | Шаблон `grep -E`, который обязан встретиться в `ir-dump-*.txt` собранного артефакта (проверяется для каждого source). Для приёмки функций чтения IR (секция `recognized-annotations`) без влияния на вывод программы |

\* Для `type=kotlin` обязательны `kind` и `desc`; для `type=gradle-image`
обязательны `expect` и `desc`.

## Примеры

Обычный exe-тест с фиксированным ожиданием:

```properties
# see docs/test-format.md
kind=exe
expect=Hello, .NET!
desc=fun main() { println("Hello, .NET!") } (EXE + runtime)
```

Dll-тест с C#-потребителем и точным ожиданием:

```properties
kind=dll
consumer=csharp-test
expect=5
desc=test_add(Int, Int): Int — минимальный pipeline (DLL + C# consumer)
```

Pe-only тест с несколькими программами:

```properties
kind=exe
backends=pe
sources=spec/*.kt
expect=OK
```

## Как это работает

Всё чтение атрибутов инкапсулировано в `scripts/tests.sh`
(source-only, подключается build/test/show-скриптами):

| Функция | Возвращает |
|---|---|
| `test_ids` / `TEST_IDS` | id всех тестов (обход каталога) |
| `test_exists <id>` | есть ли `test.properties` |
| `test_kind / test_backends / test_desc` | значения соответствующих ключей |
| `test_consumer <id>` | полный путь consumer'а или пусто |
| `test_kt <id>` | раскрытые пути исходников (по одному на строку) |
| `test_prop <id> <key> [default]` | сырое значение ключа |
| `resolve_selector <sel>` | разворачивает `all`/`last`/`<glob>`/`<id>` |

Сборка и проверка — в `scripts/build-test.sh` (диспетчер `just test` —
`scripts/test.sh`). Каждый pe-артефакт дополнительно открывается настоящим
SRM (`kotlin-dotnet-utils/verifier`) и должен выдать `VERIFIER OK`.

## Чеклист: добавить новый тест

1. `mkdir test-projects/<id>` и положить `.kt` (точку входа `main` для exe).
2. Создать `test.properties` (шаблон выше; первая строка — ссылка на этот документ).
3. Зафиксировать ожидаемый вывод в `expect`.
4. `./scripts/build-test.sh <id>` до зелёного; `just test all` — регрессия.

## Конфигурации debug/release

Каждый тест автоматически собирается и проверяется в обеих
конфигурациях (`config=debug` и `config=release`): генерация,
читаемость сборки и PDB настоящим SRM, запуск в dotnet со сравнением
вывода с `expect`. Тест-свойствам это никак не касается; точечный
прогон одной конфигурации — `build-test.sh <id> --debug|--release`
(см. docs/debug-support.md).
